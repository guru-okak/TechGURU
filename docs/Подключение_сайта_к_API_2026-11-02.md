# TechGURU: сервер и интерфейс подключены

Дата: 02.11.2026. Этот документ заменяет прежнее описание готовности этапов 2–4. Сайт работает с локальным Workers/D1 API, а не с генерируемыми заявками из JavaScript.

## Реализовано

| Пользователь | Доступные операции |
|---|---|
| Гость | Каталог активных услуг и цены из БД, активные точки приёма, регистрация и вход |
| Клиент | Создание onsite/dropoff, собственные заявки, карточка/история/смета, отмена new/confirmed, подтверждение получения dropoff, одна оценка завершённого ремонта, уведомления, профиль, фотография и смена пароля |
| Мастер | Только назначенные заявки, начало ремонта, отказ с причиной и повторный подбор, запрос деталей, ожидание и возобновление, завершение с фактическим расходом и возвратом, мобильный склад, расписание, доступность, профиль и уведомления |
| Администратор | Заявки от имени клиента, подтверждение и автоподбор, ручные кандидаты/назначение, уточнение деталей, недозвон, отклонение с причиной, отмена до назначения, смета, выдача деталей мастеру и техники клиенту, пользователи/роли/блокировка, мастера/навыки/интервалы, услуги, детали, поставщики, точки, закупки, аудит, очередь email, семь CSV-отчётов и SQL-копия |

У существующего пользователя с профилем мастера роль сохраняется: профиль связан с работами и складом. Такой аккаунт можно блокировать. Для остальных пользователей администратор может изменить роль; перевод в master создаёт профиль и мобильный склад атомарно. Собственную административную учётную запись нельзя отключить или лишить роли.

Навыки, стаж и дневной лимит мастера изменяет администратор. Мастер самостоятельно меняет контакты, доступность, форматы работы и районы. Выдачу техники после dropoff подтверждает клиент либо администратор.

## Основные правила

- Подтверждение запускает ранжирование по уровню навыка, рейтингу, дневной загрузке и количеству завершённых работ. При отсутствии кандидата остаётся confirmed + needs_manual_review. Допустим явный административный режим `manual_assignment: true`.
- Ручное назначение повторно проверяет навык, активность, канал, район, расписание, длительность, дорожный буфер onsite и дневной лимит. Заявка и бронь изменяются одной транзакцией. При использовании части длинного интервала оставшееся время сохраняется свободным.
- Ошибки валидации не создают заявку. Клиент передаёт действие, а не произвольный status. Отказ мастера возвращает assigned → confirmed; rejected используется для административного отклонения с комментарием.
- Резерв увеличивает только резерв центрального склада. Физическая выдача переносит количество с центрального на мобильный склад и снимает соответствующий резерв. При завершении выданное распределяется между использованием и возвратом; невыданный резерв освобождается. В итог входят работы и фактически использованные детали.
- Нехватка допускает частичный резерв и waiting_parts. Поставка проводится один раз; очередь потребностей обрабатывается по needed_at/id, отдельные заявки возобновляются только при полном обеспечении. При частичном обеспечении отправляется соответствующее уведомление.
- Закупки учитывают уже заказанное в pending/sent. Повторная генерация не создаёт повторных строк. Состав черновика можно редактировать; после подтверждения он фиксируется. Повторная приёмка возвращает конфликт и не увеличивает склад.
- onsite завершается в completed; dropoff — в ready_for_pickup, затем completed после получения. Автозакрытие — через три суток после completed. ready_for_pickup автоматически не закрывается.
- Пароли PBKDF2-SHA256, access 15 минут, refresh 7 дней с ротацией, httpOnly cookie, CSRF, серверные роли и проверка владельца. Смена пароля отзывает все сессии. Профильная фотография уменьшается до небольшого WebP и сохраняется в БД; фотографии заявки остаются URL по ТЗ.

## База данных

Миграции 0004–0006 применены к существующей локальной БД с сохранением данных. Осталось 21 предметное хранилище. Добавлены часы работы точек, дата отправки закупки, фотография профиля и ограничения расписания/переходов/поставщиков/ролей.

В users.full_name_fold хранится служебный ключ Unicode-поиска. API и seed обновляют его вместе с именем; поиск использует буквальную подстроку, поэтому длинные имена и символы %, * и [ не становятся SQL-шаблоном.

Канонические денежные столбцы: `services.base_price_cents`, `parts.unit_price_cents`, `requests.total_price_cents`, а также `unit_price_cents` у строк сметы, запчастей и закупок. Это INTEGER в копейках. Старые денежные столбцы в рублях сохранены для совместимости миграции; API записи обновляют обе формы, а расчёт берёт копейки. Цена 1 200 ₽ представляется как 120000 копеек. Ответы для прежней вёрстки дополнительно содержат рублёвые display-поля.

Рабочие имена `requests.user_id/service_mode`, `services.average_duration_minutes`, `master_schedule.starts_at/ends_at`, `ratings.rating` сохранены. Их соответствия учебной модели: `client_id/channel`, `duration_minutes`, `start_at/end_at`, `score`. Учебный файл из папки БД не загружается поверх миграций проекта.

Повторный seed сохраняет изменения существующих аккаунтов/цен/остатков и добавляет отсутствующие учебные записи и свободные окна на ближайшие 14 дней. Существующие занятые/пересекающиеся интервалы не перезаписываются. Предыдущие демонстрационные заявки с прошедшей датой остаются в истории; для нового ремонта выбирается будущая дата.

## Регламентные задачи и копии

Часовой scheduled handler выполняет проверки ТЗ 4.3.7: new — 2 часа, confirmed — 4 часа и флаг срочности, assigned — 24 часа, in_progress — 7 дней, waiting_parts — 14 дней, ready_for_pickup — 14/30 дней. Добавлены напоминания о выезде в пределах двух часов, повторная обработка обеспеченных потребностей и проверка закупок. Уведомления эскалаций защищены от повторов ключом события.

В локальном `scripts/dev.mjs` регламентные задачи запускаются при старте и затем каждый час, пока работает сервер. Раз в календарный день создаются SQLite-копия и SQL-дамп в `.local/backups`. Для SQL проверяется восстановление в отдельную память SQLite, целостность и внешние ключи. Кнопка администратора позволяет получить актуальный SQL-дамп вручную. Дамп содержит и миграционную историю.

Для будущего облачного развёртывания предусмотрены Cron Triggers и запись ежедневного SQL в R2 через необязательный binding `BACKUPS`. Облачные ресурсы и публикация в этой работе не создавались. Для эксплуатации в Cloudflare нужны реальный D1, секрет JWT и bucket R2 в production-конфигурации. Локальные данные хранятся в `.local/d1`; `.local` исключён из Git.

Email/SMS не отправляются во внешние сервисы: по ТЗ email реализован очередью pending. Администратор видит получателя, текст и статус в разделе уведомлений.

## Подключение интерфейса

`src/api/client.js` обрабатывает cookie, CSRF, refresh, ошибки, ограничения времени ожидания и повторные одинаковые нажатия. `src/api/workspace.js` заполняет реактивные списки данными текущего пользователя. Доступ к данным ограничивает сервер; localStorage больше не определяет роль. Ошибки сохранения не очищают формы; успешную запись не повторяем, если последующее обновление списка временно недоступно.

Vite проксирует `/api` на 127.0.0.1:8787. Уведомления и кабинет обновляются раз в минуту на видимой вкладке. Списки, фильтры, показатели, история и склад используют серверные записи. Демонстрационные операционные массивы удалены; изображения и текстовое оформление сохранены. Привязка фотографий услуг к старым ID устранена. Время показывается по Москве.

## Проверки

- TypeScript сервера и production-сборка Vue — успешно.
- 13 интеграционных тестов: базовые ограничения/seed/пароли/HTTP; полный ремонт с закупкой и FIFO; конкурирующая приёмка, два ремонта внутри длинной смены, права, административные справочники/расписание/редактирование закупки, семь отчётов, SQL-восстановление и смена пароля.
- Дополнительно 16 групп авторизации и 18 групп заявок через настоящий workerd/D1: CSRF, чужие ресурсы, недопустимые переходы, refresh replay, конкурентная бронь и отмена, искусственные ошибки с откатом транзакций, сохранение после перезапуска.
- Через браузер проверены кабинеты клиента, мастера и администратора. Проверочная заявка TGR-2026-00003 создана клиентом, подтверждена администратором, назначена автоматически, принята и завершена мастером; клиент отправил оценку. Эта учебная запись оставлена для просмотра.
- Проверены мобильный вид 375 px, отсутствие горизонтального переполнения и отображение карточки ремонта. По мере проверки устранены ошибки обращения к демонстрационным контактам точек.
- Проверка рабочей локальной БД: foreign_key_check без нарушений, quick_check=ok.

Нагрузочная проверка на 100 одновременных пользователей и облачная приёмка не проводились; показатели production нельзя выводить из локальных функциональных тестов.

## Запуск

Из папки проекта в двух терминалах:

```powershell
npm run dev:api
npm run dev
```

Сайт: http://127.0.0.1:5173/ . API: http://127.0.0.1:8787/api/health . После изменения серверного кода процесс API нужно перезапустить. Локальная миграция — `npm run db:migrate`; повторяемое учебное наполнение — `npm run db:seed`; проверки — `npm run typecheck:server`, `npm run test:server`, `npm run db:check`.

Кнопки учебных аккаунтов на странице входа подставляют реальные демонстрационные учётные данные. Роль определяет только ответ сервера. Серверная БД и вёрстка сохранены до изменения в резервной папке `Резервные копии/Перед_подключением_API_20261102_220308` в корне курсовой.
