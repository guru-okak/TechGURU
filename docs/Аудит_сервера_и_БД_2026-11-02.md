# Аудит серверной части и базы данных TechGURU

Дата: 02.11.2026. Проверена текущая локальная версия проекта.

## Результат

Основа сервера работоспособна: Workers API, локальная D1, 21 предметная таблица, авторизация и начальная обработка заявок. Переписывать сервер с нуля не требуется. Полного функционала системы пока нет; сайт работает на демонстрационных данных отдельно от API.

Рабочие миграции и итоговый учебный комплект БД описывают одни предметные сущности, но различаются именами полей, денежными единицами и ограничениями. Подменять работающую БД файлом из учебного комплекта нельзя. Сначала нужны согласованная модель и миграции с переносом данных.

В этом аудите бизнес-код, интерфейс, применённые миграции и содержимое рабочей БД не изменялись. Добавлены отчёт, повторяемая дополнительная проверка и её JSON-результат. Изменяющие HTTP-сценарии выполнялись на отдельных временных D1, удаляемых тестовыми фикстурами после проверки.

Облачное развёртывание, нагрузка 100 пользователей, внешняя отправка сообщений и восстановление production-БД не проверялись. Наличие таблицы не означает наличие реализованного бизнес-процесса. Проверка существующего тестового набора не является полной проверкой безопасности.

## Расхождения и недостатки

### 1. Деньги: до подключения API нужно устранить риск ошибки в 100 раз

В итоговом документе цены — INTEGER в целых копейках. В рабочих миграциях поля `base_price`, `unit_price`, `total_price` имеют REAL; seed и существующий API-тест трактуют 1200 как цену 1200 рублей. В SPEC уже записано хранение в копейках, то есть код отстаёт и от рабочей спецификации.

Решение: единая модель INTEGER-копеек внутри БД и вычислений, явное преобразование при показе рублей. Перенос существующих сумм через отдельную миграцию с проверкой округления, диапазона и смет. Одной смены SQL-типа без пересчёта недостаточно. Контракт API должен явно определять единицу цены.

### 2. Нет кандидатов: подтверждение не доходит до ручного разбора

`confirmRequest`, `confirmSlot` и SQL `confirm` требуют существования свободного окна. На отдельной D1 проверено: при отсутствии окон запрос подтверждения возвращает 409, заявка остаётся `new`, `needs_manual_review=0`.

По ТЗ 4.3.3 отсутствие подходящих кандидатов после подтверждения должно оставлять заявку в `confirmed`, выставлять флаг ручного разбора и уведомлять администратора. Сейчас подтверждение всегда ставит флаг ручного назначения, если окно существует; автоподбора ещё нет. Это временная реализация предыдущего этапа, которую необходимо заменить полноценным сценарием подтверждение → подбор → назначение либо ручной разбор.

### 3. Допустимое описание не помещается в HTTP-лимит

Контракт разрешает описание до 2000 символов, а `readJson` ограничивает всё тело 4096 байт. Подтверждено: 2000 русских букв с минимальными полями дают 4251 байт и ответ 413. Дополнительные адрес, контакт и до пяти URL увеличивают размер.

Решение: согласовать ограничения длины полей и общий байтовый лимит, сохранив защиту от чрезмерных запросов. Добавить граничные проверки кириллицы и фотографий.

### 4. Различия схемы учебной и рабочей БД

Ниже рабочее имя слева, имя итоговой модели справа. Сами различия имён не являются потерей функциональности, но требуют явного сопоставления.

| Таблица | Рабочая схема | Итоговая учебная модель |
|---|---|---|
| requests | `user_id`, `service_mode` | `client_id`, `channel` |
| services | `average_duration_minutes` | `duration_minutes` |
| master_schedule | `starts_at`, `ends_at` | `start_at`, `end_at` |
| request_items | `name` | `description` |
| ratings | `rating` | `score` |
| service_points | Нет `working_hours` | Есть `working_hours` |
| purchase_orders | Нет `sent_at` | Есть `sent_at` |
| Денежные поля | REAL, текущие значения в рублях | INTEGER, копейки |

В рабочем проекте также есть полезные служебные дополнения: `refresh_jti`, `request_number`, `version`, `last_operation_id`, `event_key`, `assigned_at`, `cancel_reason`, `cancelled_by`, `event_type`, счётчик попыток очереди. Их необходимо сохранить. `masters.rating` хранится в рабочей БД, а учебная модель рассчитывает рейтинг представлением; при реализации оценок нужен единый способ обновления/вычисления.

Рекомендация: сохранить существующие рабочие имена через явную таблицу соответствий, добавить недостающие предметные поля и ограничения. Массовое переименование не нужно для запуска функционала. Если потребуется буквальное совпадение DDL с документом, выполнить отдельную проверяемую миграцию; не загружать учебный DDL поверх рабочих таблиц.

### 5. Учебные ограничения ещё не перенесены в рабочую схему

В рабочих миграциях четыре триггера: проверка оценки при вставке/изменении, генерация и неизменность номера заявки. В итоговом SQL дополнительно проверяются роль профиля мастера, соответствие поставщика строке закупки, расписание и владелец брони, разрешённые переходы, причина отклонения и задержка закрытия. В рабочей схеме также слабее проверки дат и некоторых типов.

Доступные операции API частично защищены сервисами и условными SQL-записями; отсутствие SQL-триггера само по себе не доказывает обход через API. Однако для ещё не реализованных модулей защиты пока нет. Нужны новые миграции и отрицательные проверки. Перенос триггеров расписания требует адаптации: нынешнее назначение сначала меняет мастера, затем освобождает старую бронь. Нельзя добавлять ограничения без проверки порядка операций и переназначения.

### 6. Бронь занимает всю строку расписания

Текущее назначение устанавливает `is_booked=1` на выбранной строке `master_schedule`. Если в будущем строка будет означать целую смену, один ремонт заблокирует всю смену. Текущий seed использует короткие окна, поэтому это прежде всего ограничение модели, а не доказанная ошибка сегодняшнего интерфейса.

До реализации управления расписанием закрепить: строки — отдельные окна записи либо интервалы доступности с отдельным учётом фактической занятости. Проверить два последовательных ремонта и работу дольше одного двухчасового слота. ТЗ 4.3.3 упоминает длительность + буфер 30 минут; текущий код добавляет буфер только onsite, как записано в SPEC. Эту трактовку явно закрепить в документации реализации и тестах.

### 7. Фронтенд ещё не подключён к серверу

`useSession.js` хранит демонстрационную роль в localStorage; списки используют `src/data/*` и `mockApi`. Каталога `src/api` пока нет. Vite не проксирует `/api`; браузерные страницы и Worker работают на разных портах. Нельзя просто заменить данные на fetch без настройки общего origin и cookie-сценария.

Нужно: API-клиент, proxy в разработке, единый источник состояния пользователя, CSRF, refresh и обработка 401/403/409/422, загрузка/ошибка/пустой результат. Для схемы same-origin сохраняются текущие строгие cookie и проверка Origin. Демонстрационный переключатель роли не должен давать доступ в рабочем режиме. Справочники и идентификаторы демо-UI отличаются от seed сервера; их нельзя связывать по совпавшему числу id.

### 8. Документация запуска отстаёт

`docs/backend-local.md` и начало `docs/architecture.md` всё ещё говорят о предварительном документе с SQL только для шести таблиц и первоначальном этапе сервера. Итоговый учебный комплект уже содержит 21 таблицу. Старые инструкции полезны как история, но не являются актуальным перечнем готовности. SPEC также содержит последнюю запись о фазе вёрстки; ниже добавлена запись о начале аудита сервера.

## Порядок дальнейшей реализации

1. **Согласовать рабочую БД с моделью:** копия перед изменениями, денежные единицы, недостающие поля/ограничения, сопоставление имён. Проверять и создание пустой БД, и обновление существующей без потери данных.
2. **Довести API заявок и подбора:** лимит JSON, отсутствие кандидатов, полный набор переходов, кандидаты/ранжирование/расписание, контроль конкуренции.
3. **Подключить вход и первый клиентский сценарий:** реальная сессия → создание → сохранённая карточка → отмена; затем обработка администратором и работа мастера.
4. **Ремонт, склад и закупки:** полные транзакции, поставка, FIFO, смета, выдача и оценка.
5. **Завершить остальные экраны:** справочники, уведомления, аудит, отчётность; добавить Cron и резервирование, провести сквозную приёмку и подготовить развёртывание.

Начинать следует с пункта 1: иначе при подключении интерфейса закрепятся разные единицы цен и несовпадающие контракты. Вёрстку и расположение экранов при этом сохраняем.
